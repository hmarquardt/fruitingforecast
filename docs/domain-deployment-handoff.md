# Production domain handoff

The application-domain migration completed on 2026-09-20.

- Cloudflare Pages project: `fruitingforecast`
- Canonical application: <https://fruitingforecast.com/>
- `www`: permanent redirect to the matching apex path and query
- GIS origin: <https://data.hanksjunkdrawer.com/>
- Rollback/reference: <https://hmarquardt.github.io/junkdrawer/fruiting-forecast.html>
- App/scoring/GIS: `2026.09.20.6` / `FF-1.7.0` / `content-db0f839a4352ef82`

The deployed artifact is generated by `tools/stage_pages.py` from an explicit runtime allowlist, then uploaded with Wrangler. The R2 CORS policy now permits the apex, `www`, and Pages project hostname while preserving every prior valid origin and the existing GET/HEAD/Range contract. No Parquet object, manifest object reference, biology, profile mapping, or scoring logic changed.

The optional future `data.fruitingforecast.com` migration should remain separate. The current GIS origin is stable, cacheable, independent from application hosting, and fully accepted from the new domain. A branding-only hostname change would require DNS/R2 custom-domain work, CORS and manifest coordination, cold-cache/browser QA, and compatibility planning without improving forecast behavior. Keep `data.hanksjunkdrawer.com` until a clear operational or branding benefit justifies that risk.

If that migration is later approved:

1. Bind the new hostname to the same R2 bucket without rewriting objects.
2. Add and verify CORS before changing the manifest origin.
3. Validate GET, HEAD, Range, digest/length checks, DuckDB, cold/warm cache, and all 13 profiles.
4. Retain the old data hostname through an explicit compatibility period.
5. Bump only the application version for an origin/configuration change; keep scoring and dataset versions unchanged.

No manual action remains for the application-domain cutover. Direct Upload deployments remain deliberate operator actions after accepted `main` changes.
